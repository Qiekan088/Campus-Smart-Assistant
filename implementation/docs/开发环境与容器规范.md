# 开发环境与容器规范

版本ENV-0.2，2026-11-12。依据本轮用户决定：统一本机npm版本、同机前后端、采用Docker并预留数据库打包；用户接受此前令牌和超时建议。本文件规定ENV-0.2环境；构建和运行已验证，证据见环境验证记录，但不代表V0业务验收。

## 工具与依赖

实测命令node --version / npm --version / docker --version / docker compose version：Node.js 24.14.1、npm 11.11.0、Docker CLI 29.1.3、Compose v2.40.3-desktop.1。前端宿主机与镜像内均锁Node.js 24.14.1和npm 11.11.0，不假定基础镜像自带npm版本正好一致；A在构建时检查。Docker/Compose为本机观察值，不强制其他操作系统安装相同Desktop补丁，须支持本项目Compose功能并实测。

A维护package.json与package-lock.json，用npm ci复现已锁依赖；初始生成及有意更新依赖才运行npm install并审查锁文件。不得混用其他包管理器锁文件。Python固定3.12.12，MySQL固定8.4.4，后端Linux hash锁文件为app/backend/requirements.txt；B维护并由C/D共同复核；禁止使用latest作为可复现基线，镜像记录精确标签及验证后的digest。未验证的镜像标签不可声称可用。

## 同机拓扑

标准联调使用同一电脑上的Docker Compose。V0服务为frontend和backend，C/D为backend内模块，V0使用单后端进程的模拟仓储。V1再增加db及worker。Docker是本地开发环境工作，不新增公网部署或运维岗位。

| 位置 | 地址/职责 |
|---|---|
| 浏览器 | http://127.0.0.1:5173；业务请求只使用/api/v1 |
| frontend容器 | 进程监听0.0.0.0:5173；宿主仅映射127.0.0.1:5173 |
| frontend开发代理 | /api转发http://backend:8000，保留/api路径；目标配置仅在开发服务端使用 |
| backend容器 | 进程监听0.0.0.0:8000；宿主调试映射127.0.0.1:8000 |
| db容器（V1） | 后端/Worker使用db:3306，默认不发布宿主端口 |
| worker（V1） | 共用后端镜像，独立进程，无HTTP端口 |

容器内localhost是该容器自己；浏览器不能解析backend/db服务名。宿主机直接启动的可选调试方式：前后端监听127.0.0.1，代理目标改为http://127.0.0.1:8000；不可与容器方案同时争用同一端口。跨电脑联调延期，当前不要求开放防火墙或局域网监听。端口冲突须显式报错，不自动换端口导致规范失配。

## V0配置值

| 配置名 | 默认值 | 维护位置 |
|---|---|---|
| SESSION_TTL_SECONDS | 7200 | B后端运行配置 |
| REQUEST_TIMEOUT_SECONDS | 10 | B产生deadline，C/D遵守 |
| DEV_PROXY_TIMEOUT_SECONDS | 15 | A的Vite服务配置 |
| CLIENT_TIMEOUT_MS | 20000 | A客户端 |
| API_PROXY_TARGET | http://backend:8000 | frontend容器内Vite配置 |

令牌绝对有效期2小时，不随请求延长，不增加刷新令牌或空闲超时；这些是V0规则，后续变更另记。令牌仅保存在前端内存，刷新页面需要重新登录。退出立即撤销当前令牌；401清理私人缓存并提示登录。过期由后端执行，不靠浏览器计时。测试可覆盖为60秒并标注测试配置，演示默认值不变。前后端普通HTTP仅用于本机合成演示，正式扩展再确认TLS等条件。

C/D耗时处理在10秒后不得提交；代理15秒、浏览器20秒只是等待上限。断开不保证取消，重试仍使用原幂等键；不因超时创建新提交意图。真实模型接入V1需重新评估期限与预算。

## 容器交付边界

V0编码任务需要交付根compose.yaml、app/frontend/Dockerfile、app/backend/Dockerfile以及相关.dockerignore、无密钥的.env.example和启动说明；这些文件已生成并用于实际构建。Compose项目名固定campus-qa，避免中文目录名推导不合法项目名。A维护前端镜像、锁文件和代理；B汇总Compose及后端镜像；C负责未来Worker命令与数据路径，D负责模型配置说明；共享变更由调用方复核。

Windows宿主node_modules和.venv不复制进Linux容器；前端仅挂载源码和开发配置，node_modules保留在镜像，避免旧volume遮蔽新依赖。依赖锁文件变化后按说明重新安装/构建，不能沿用陈旧volume证明复现成功。开发热更新与端口在真实浏览器验证。

构建上下文排除.git、.env、密钥、个人数据、node_modules和.venv；.env.example只有变量名和无敏感示例。数据库凭据和模型密钥运行时注入后端，不写镜像层、前端构建变量或日志。不挂载Docker socket、不使用privileged作为默认配置。容器不能被宣称为执行任意不可信程序的绝对安全沙箱。

## 数据库与持久化扩展

V1采用独立MySQL服务和命名数据卷，数据库不打进应用镜像，不将数据库文件提交Git。应用使用受限业务账号，迁移权限单独安排；backend与worker共享明确的文件/索引存储路径，具体设计由Q-DEV-03/05落实。应用启动前数据库健康检查及迁移成功是就绪条件；depends_on启动顺序本身不证明数据库可用，失败须有有界重试和明确错误。

迁移由单次受控步骤运行，禁止每个Worker并发迁移。普通停止/重建不得删除数据卷；清理数据是单独明确操作，禁止将down -v写成日常停止命令。验收需验证重启后数据仍在；命名卷不等于备份，正式备份方案仍不属于本轮范围。

# 分阶段实现与测试计划

当前：V0准备。用户确定三版实现V0/V1/V2和一版系统测试V3。每版均有测试，V3集中整理系统性验证与测试文档；不是前三版不测试。服务器与公网暂不涉及，验收在约定局域网环境开展。

## 全员阶段门槛

每版：明确Q/ADR及需求→细化当前接口与关键设计→人工核对测试预期→任务准入与实施→模块检查/交叉审查/联调→ABCD全员验收→记录下一版准入。每名成员是自己模块负责人，也是全链路验收参与者；不能只说“我的完成了”。

上一版未满足以下全部条件时，不启动下一版实现：
1. 当版必做任务完成，关键问题及阻塞Q已解决；如需改变范围，由四人明确决定并同步，不能靠“暂不做”自动过关。
2. 完整主流程和至少一个关键异常有实际演示与证据，相关模块测试及前版回归达到已确认标准。
3. 需求、架构、接口、测试和任务状态与实际代码一致，关键变更经另一名真实成员复核。
4. ABCD四位实际成员在阶段验收记录对同一份基线均明确“通过”，有身份、时间、依据和真实确认出处；缺一、需修改、待核验均不放行。
5. 基线维护人汇总并记录放行，不能替成员投票。没有Git提交可用唯一快照ID和文件清单/哈希，绝不伪造提交号。签署后相关代码/契约改变即形成新基线，旧签署不能直接沿用。

AI只汇总实际确认、写验收建议；不能因测试全绿或四个AI都同意而代签。若某成员受阻，仅暂停依赖项，其他人继续当前版无关任务；全员通过前不跨版开发。可提出下一版问题，不能预先实现。

V1内部先人工片段打通真实检索问答，再接上传解析发布，不新增版本号。C/D使用已确认契约的模拟输入并行，第一轮即真实对接，不到末尾才联调。V2由A/B集中做工单，C/D做各自主责质量完善；工作量按真实风险协商，不按页面数平均。

## 文档责任

每版开始只细化当版。A补交互/API消费，B补业务状态数据接口，C补任务/索引/检索，D补问答事件/模型核验；共享架构和接口由双方更新，基线维护人只组织索引。各人留自己的任务、测试、关键AI纠错证据，证据索引不归某人事后补造。V3分别供稿汇成测试文档，不预填运行数量或通过率。

建议交叉检查A↔B、C↔D，跨对象事务由C或D再查B，最终四人查整条业务链；可按任务调整审查人，但不能作者独审。具体成员姓名和轮值在实际开工时登记，不凭角色字母虚构签名。

## 阶段准入与任务状态

任务准入须具备输入基线、负责人/另一成员审查人、允许修改范围、依赖、可检验预期、测试数据及启动配置。任务顺序：待准备→可开始→实现中→待审查→需修改或已完成。已授权的明确任务不反复询问；接口/需求/新依赖超出授权时先列问句。当前文档初始化不等于V0已获四人验收。

测试失败先判责：实现不符修实现；测试预期有误需依据和实际成员批准；需求冲突重开Q。禁止删除约束或放宽断言追求全绿。并发须真实MySQL多连接，不以SQLite或内存Mock替代MySQL证据；局域网两台实际电脑检查访问，不用单机localhost充当。

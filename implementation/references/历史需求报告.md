# 校园事务问答与咨询工单系统需求规格说明书

版本 1.0　编制日期 2026年11月12日

本报告定义面向在校师生的公开事务咨询与异步工单服务。系统以可追溯的公开资料为依据，回答办理步骤、地点和材料等问题；条件不完整时澄清，缺乏依据或涉及个人资格裁量时引导转人工。正文按项目概述、用户需求、领域与数据、规则与权限、行为与状态、质量要求、验收与验证、基线与人机协作八章组织。

# 第1章 项目概述

## 1.1 业务问题与项目背景

学校办事信息分布在多个部门页面，部分事项随校区、身份、图书来源等条件变化。用户只问“能续借吗”，未说明借的是哪一类图书，系统就不能直接给出统一结论。即使网页仍可访问，也不能据此保证其中的历史说明仍然适用。

本项目围绕公开办事说明，建立“资料来源—知识版本—问答记录—人工工单”的业务链。首批资料采用宁波大学梅山校区公开页面，以图书借还、校园卡和网络服务说明作为分析样本。用户需求来自公开资料分析及课程项目范围决定，具体服务量、用户习惯和业务部门工作时段仍需实际调研确认。

## 1.2 业务目标与成功指标

本节定义业务效果；1.5节说明支撑需求的资料和依据，两者不重复登记。

| 目标 | 成功表现 | 检查方式 |
|---|---|---|
| G-01 答复有据 | 每条依据答复均能定位知识版本、来源和引用快照 | 逐条核对答复要点与原文 |
| G-02 缺依据不猜 | 缺条件先澄清，无法支持的金额、时限和资格判断不生成结论 | 正例与拒答反例走查 |
| G-03 历史可追溯 | 新答复只使用当前可用版本，旧答复保留当时内容并显示当前状态 | 停用前后对照 |
| G-04 人工交接完整 | 工单、问答关联与会话转人工一起生效，失败时全部不生效 | 成功、失败与重复提交场景 |
| G-05 处理责任明确 | 仅取得处理权的客服回复，由用户确认解决 | 权限与状态转换检查 |

这些目标不预设命中率、每日工单量或高并发规模。数值目标需结合样本、使用条件和实际观察确定，不能把课程样本结果直接推广到全校服务能力。

## 1.3 涉众与责任

| 角色 | 目标与责任 | 系统操作边界 |
|---|---|---|
| 问答用户 | 获取公开说明，补充条件，确认问题是否解决 | 提问、本人记录、本人工单、反馈 |
| 人工客服 | 接收未解决问题并提供处理回复 | 领取、查看可访问工单、回复、请求确认 |
| 知识维护 | 保持知识有来源、有版本、可复核 | 登记来源、编辑草稿、发布、停用和复核 |
| 管理者 | 维护角色与运行概况 | 角色授权与统计，不自动取得私人内容访问权 |
| 业务部门与领域专家 | 确认制度现行性和适用范围 | 在系统外提供业务意见，不强设专家账号 |

客服和知识维护可以由同一账号兼任，但兼任不扩大对象访问范围。公开页面的核对只能证明页面所载内容，不能代替学校业务部门对现行政策的确认。

## 1.4 系统范围与非目标

首版覆盖四条主线：知识来源与版本维护、依据问答、异步咨询工单、本人记录与反馈。用户得到有依据的说明后可结束咨询；未解决时转工单，客服回复后由用户确认解决或继续补充。

系统不实施学籍、资格、费用或处分审批；不自动办理校务；不建设实时客服排队、多渠道接入、复杂调度或学校统一身份认证。课程原型采用本地演示账号，外部模型通过可配置接口接入，不要求自部署大模型、微调或独立向量数据库。

## 1.6 运行条件与约束

项目按小型Web系统组织，支持浏览器访问；核心原型采用Python标准库、SQLite与普通网页，默认离线检索演示，避免把付费模型配置作为本地查看流程的前提。真实模型模式由后端读取接口地址、模型名及密钥，密钥不进入前端、仓库和交付文档。

工单采用异步处理，不承诺实时在线或全天候服务。服务时段、资料保留期限、业务复核责任人和正式部署要求在扩大试用前确认。

## 2.4 核心详细用例

### 2.4.1 UC-01 依据支持的问答

目标是给出被公开原文支持、适用条件匹配的说明。参与者为已登录用户及系统，触发事件为用户提交问题。系统先记录问题，再识别校区、身份、事项对象等条件；缺项则澄清，条件完整后检索已发布且当前可用版本，检查冲突，生成或整理答复要点，校验引用和要点，最后在输出事务中复核版本与会话状态，保存引用快照并展示来源。

替代流程包括：缺条件时最多补充两轮；仍无法判断则提示无法确定并给出人工入口；无依据时不编造结论；同事项、同条件确有矛盾时展示各方依据，交人工判断。外部模型超时、引用越界或增加原文不支持的结论时，整条生成内容不展示。

成功结果是一条带来源、知识版本及快照的问答记录。失败或拒答也保留问题和结果类型，但不伪造有效答复快照；在途版本被停用或会话已转人工时记录中断，不发布旧结果。验收采用“真诚馆借的书在梅山怎么还”的有据答复，以及“超期每天罚多少钱”的无依据拒答。触发规律为每次咨询提交，实际使用频率待真实日志确认。

### 2.4.2 UC-02 知识新增与发布

参与者为知识维护人员，触发为新增办事说明或修订已有说明。前置条件是具备维护权限并取得可核对原文。维护人员登记来源标题、机构、地址、页面日期和摘录，再建立草稿，填写正文、适用条件、答复要点与时间信息。发布时检查来源、摘录和内容完整性，同一事务停用该条目旧发布版本并发布新版本，记录操作人与理由。

缺来源、摘录不可读或必填内容不完整时保持草稿；编辑已发布内容生成新草稿，不能原地覆盖。并发发布以同一初始状态为依据核验，发生竞争时拒绝过时操作；顺序进行的两次合法修订可各自发布，最终仍只有一个发布版本。数据库写入失败时旧版本和草稿均保持原状。

验收检查无来源不能发布、新版生效时旧版停用、历史快照仍可打开、无权角色无法维护。发布由资料变更或复核结论触发，不编造每月发布次数。

### 2.4.3 UC-04 咨询工单闭环

参与者为用户与客服，触发为用户选择转人工或主动提交咨询。系统带入必要的原问题、结果类型与依据摘要，用户确认主题和描述后提交。工单保存、关联问答与会话转人工必须一起提交，随后停止该会话自动答复。

客服从待处理队列领取，首个成功者获得处理权并进入处理中；回复后转待用户确认。用户确认解决则关闭，补充问题则回处理中。用户可在待处理或处理中撤销；客服不能代用户确认、关闭或撤销。关闭或撤销后再咨询应新建后续工单，并保留与原单的关联。

同一幂等键同内容返回原结果，同键不同内容拒绝；同一会话换键重复提交也只返回原工单。保存失败不改变会话模式，原输入可重试。两名客服同时领取仅一人成功；撤销与回复竞争按提交后的实际状态检查，终态不再接受回复。

验收包括完整闭环、重复提交、双客服竞争、保存失败回滚和越权访问。工单数量、处理时段和响应承诺须由实际服务安排确定。

### 2.4.4 其他用例

UC-03规定停用、到期、待复核和在途答复联动：停用必须说明理由；新答复不再使用该版本；历史答复及快照保持原样，查看时计算失效标记。到期和待复核属于可用性判断，不增加知识生命周期状态。被引用版本不能删除。

UC-05规定用户对本人答复选择有帮助、未解决或内容纠错。同一问答每人至多一条反馈，再次提交更新原条目；撤回后可重新提交。反馈只进入维护线索，修订仍须通过草稿发布流程，不自动改写知识。

## 2.5 交互与页面需求

用户端提供提问、澄清、来源详情、本人问答和工单详情。答复先显示结论，再显示支持要点、来源标题与日期、适用条件及快照入口。离线演示与真实模型模式清晰区分；合成冲突样本明确显示其演示性质。

澄清提示指出缺失条件；最多两轮的限制按当前澄清链计数，不限制整场会话中独立完整问题的数量。转人工保存成功后显示工单入口；失败时保留输入。工单按钮依据角色、对象与状态展示，但实际授权以服务端检查为准。切换账号后清除前一人的私有内容和输入。

## 2.6 外部接口与人工交接

资料来源接口保留地址、页面日期、摘录与核对信息，首版由维护人员录入。外部模型只接收脱敏问题和筛选后的公开片段，返回引用及原文支持要点，最终显示内容由系统核验后组装。账号、密钥、私人工单及附件不发送给模型。

人工交接只提供处理本工单所需的原问题、条件、答复结果、关联依据及用户补充。客服不能通过工单获得用户其他私人记录。外部服务失败时记录失败类别并提供替代路径，不把失败伪装成正常答复。

# 第3章 领域与数据

## 3.1 统一术语

知识条目表示一个稳定业务主题；知识版本表示该主题某一版具体说明；来源登记描述原始公开资料；来源摘录用于维护时核对；引用快照保存某次答复采用的依据。会话组织交互，问答记录保存一次问题与结果，工单承载异步人工处理，反馈提供用户评价线索。

“已发布”是生命周期状态，“当前可用”是结合时间、复核、摘录和条件得到的判断；不能把二者等同。来源摘录与答复快照也不合并：前者服务维护，后者保证历史可追溯。

## 3.2 核心对象与关系

一个条目具有多个版本，同条目最多一个版本处于已发布状态。一个来源可有多个摘录，一个版本关联其依据。一次问答可引用多个版本，并保存对应快照。一个会话包含多条问答，至多关联一张转人工工单；后续咨询采用新会话或关联原单的新工单。工单包含多条处理记录，问答可有一条本人反馈。

图3-1领域类图位于附件models目录。该图表达业务对象、职责及多重性，不提前把全部对象固定为数据库字段或实现类。关键协作是问答读取版本、输出前再核验，工单读取关联问答；反馈只提供线索，不直接驱动知识版本变化。

## 3.3 对象职责

| 对象 | 主要职责 | 必须保持的约束 |
|---|---|---|
| 知识条目与版本 | 维护主题、内容、条件及发布历史 | 已发布内容不可原地覆盖 |
| 来源与摘录 | 保存依据及取得信息 | 页面日期不冒充生效日 |
| 问答与引用快照 | 保存问题、结果与当时依据 | 完成后内容不静默改写 |
| 会话 | 组织澄清及自动/人工模式 | 转人工成功后不继续自动输出 |
| 工单与处理记录 | 分配处理权、记录回复和确认 | 终态不可继续回复 |
| 反馈 | 记录本人评价和纠错线索 | 不直接修改知识 |

## 3.4 关键数据字典

| 数据 | 含义与来源 | 约束及维护角色 | 隐私与访问 |
|---|---|---|---|
| 来源元数据 | 原网页标题、机构、地址、页面日期、取得日 | 维护人员核对；未知日期不补造 | 公开资料 |
| 适用条件 | 校区、身份、图书来源等范围 | 由原文整理，缺条件先澄清 | 随知识版本公开 |
| 生效与复核信息 | 生效起点、失效点、复核时间与截止期 | 维护人员设置，注明依据与精度 | 随引用展示必要信息 |
| 问题与结果 | 用户输入、结果类型、时间、会话关联 | 系统生成记录，不用猜测补齐输入 | 本人及有授权客服 |
| 引用快照 | 本次采用的原文、版本和来源标识 | 答复提交时保存，后续不改写 | 跟随问答授权 |
| 工单与回复 | 主题、描述、状态、处理人、操作时间 | 用户和取得处理权的客服各按状态维护 | 本人、允许接单或已分派客服 |
| 反馈 | 类别、说明、时间与关联问答 | 本人更新；维护侧只看必要线索 | 不公开私有问题正文 |

## 3.5 生命周期与保留

已引用版本、历史问答和快照形成追溯链，不能通过删除被引用版本破坏历史。保留期限、删除申请与备份恢复策略在正式试用前确认。课程阶段使用演示数据，不据此承诺真实校务数据的长期保管能力。

# 第4章 规则与权限

## 4.1 统一业务规则

本章是业务规则的权威定义；第5章引用规则表达状态变化，第6章规定质量情境，不重复另定口径。

| 规则组 | 核心约束 |
|---|---|
| BR-REQ 依据 | 只用当前可用、适用匹配的已发布版本；引用须在候选集合内，所有显示要点均有原文支持 |
| BR-ASK 澄清 | 先问缺失条件，当前链最多两轮补充；不从“我”猜学生，也不从“借的书”猜图书来源 |
| BR-CONF 冲突 | 同事项同条件下结论互不相容才算冲突；可并行办理方式和不同事项不算 |
| BR-EXP 可用性 | 停用、未生效、到期、待复核、摘录不可读均阻止新答复；来源不可达需结合现存依据判断 |
| BR-KB 维护 | 编辑已发布内容形成新草稿；新旧版本原子切换；被引用版本不能删除 |
| BR-REP 重复 | 按提交意图及幂等键判重；不按主题或时间窗合并不同人的咨询 |
| BR-TK 工单 | 仅用户确认解决才能关闭；客服回复请求确认，不代替用户做确认 |
| BR-FB 反馈 | 本人唯一反馈可更新或撤回，纠错只生成线索 |
| BR-PERM 权限 | 同时核角色、对象归属和状态；自然语言声明“我是管理员”不产生权限 |

时间口径统一采用可比较的带时区时间。完整时间戳按精确时点判断；仅日期的失效和复核截止期含当日，到次日00:00 UTC起阻止使用，页面清楚展示精度。生效开始包含起点。页面发布日期不直接决定知识是否生效。

## 4.2 角色、对象与状态权限

| 操作 | 用户 | 客服 | 知识维护 | 管理者 |
|---|---|---|---|---|
| 提问及本人记录 | 本人 | 不因客服身份获得 | 不因维护身份获得 | 不查看他人正文 |
| 待处理队列 | 不可 | 可领取必要条目 | 不可 | 仅统计 |
| 工单详情及回复 | 本人查看与补充 | 未分派待处理可接单，已分派仅处理人回复 | 不因维护身份获得 | 不查看正文 |
| 确认解决或撤销 | 本人按状态执行 | 不可代执行 | 不可 | 不可代执行 |
| 来源及知识维护 | 不可 | 需另具维护角色 | 可维护 | 需另具维护角色 |
| 角色授权 | 不可 | 不可 | 不可 | 增量功能 |

兼任账号逐项核验权限，不能因为具有维护权限而读取无关工单。前端隐藏按钮仅用于提示，直接构造请求仍须被后端检查。

## 4.3 跨对象一致性与竞争

转人工时工单写入、问答关联与会话模式切换在同一事务内完成。任一步失败均不产生半成品；同会话重复提交返回原单。工单提交内容不同却复用同一键时拒绝，不通过覆盖旧描述实现“重试”。

问答生成可在事务外调用模型，但最终输出必须在提交边界重新读取知识与会话。停用或转人工先提交时，在途自动答复必须中断。反之，已经合法提交的历史答复保留，不因后续停用而改写。

两名客服领取、撤销与回复、同条目并发发布都需检查提交后的真实状态；竞争失败返回明确结果且不写业务数据。详细状态对应第5章，验收情境对应第7章。

## 5.1 核心流程

主流程从问题提交开始，依次判断适用条件、候选可用性、冲突及引用支持。澄清返回用户补充输入，而不是在一次请求中无限循环；无法支持结论时保留问题并给转人工入口。人工交接只有保存成功后才改变会话模式。

## 5.4 时间事件与异常联动

系统在使用知识时计算到期与复核状态，不依赖定时任务先把状态改为“过期”。来源暂不可达但已有可读、经维护复核的摘录时可以带提示转述，不能保证其现行性；摘录缺失则阻止新答复，历史答复保持内容并标注问题。

生成中停用、生成中转人工、发布新旧版本切换、重复工单和双客服领取属于重点竞争场景。并发测试应使用真实文件数据库和多个连接，不能把顺序请求称为并发证据。

## 5.5 对象协作

问答服务依次读取会话、筛选版本、获取模型要点、最终核验并保存问答及快照；工单服务关联原问答并原子转人工；客服服务只更新已授权且状态允许的工单。图5-5a、5-5b、5-5c分别展示问答、原子转人工和领取回复的顺序，图源及清晰导出在附件models目录，避免把整张长顺序图缩小到不可读。

# 第6章 质量要求

## 6.1 依据性与正确性

答复质量从原文支持、适用条件、引用一致性和拒答得当四方面评价。所有依据答复均应能逐点在采用的公开片段中定位支持内容；只存在一个正确引用，不代表整段自由生成文字均受支持。

质量样本至少包含可答、缺条件、无依据、合成冲突、到期或待复核、越权、转人工七类。合成样本只用于验证系统行为，不评价真实政策正确性。调试时反复使用的问题与后续独立评价问题分开登记。

## 6.2 安全、隐私与可靠性

输入和工单均按普通内容处理，不能用提示词改变角色。后端持续检查对象范围；切换账号清除上一人的私有输入。外发前处理明显的口令、证件、学号和联系方式；密钥只保存在后端配置中。

成功业务与必要关联记录共同提交，失败时不留半成品。审计记录必要的操作者、动作、对象、结果和时间，不记录密钥和无关敏感材料；失败审计不能因与未回滚事务相互等待而丢失或拖住业务。

## 6.3 性能、易用性与维护性

性能目标以课程演示和小规模试用为条件，先记录运行环境、数据量、请求模式及响应分布，再确定可承诺指标。当前不规定无依据的高并发、全天候可用率或秒级恢复承诺。

用户应能看清来源日期、适用范围、当前状态以及下一步操作。参数与模型配置集中管理；增加知识条目应通过维护流程完成，而不是修改代码或硬编码固定问句。

## 6.4 质量情境与检验方法

| 情境 | 必须观察的结果 | 方法 |
|---|---|---|
| 有依据问题 | 支持要点、来源、版本、快照一致 | 样本逐点核对 |
| 缺关键条件 | 先澄清，未补全前不给结论 | 两轮澄清与新问题场景 |
| 模型失败或越界 | 不展示无效结论，保留问题和人工入口 | 故障及恶意输出注入 |
| 停用与历史 | 新答复禁用，旧答复不改写 | 在途控制与停用前后对照 |
| 重复及并发 | 唯一业务结果，冲突方不写业务数据 | 多连接屏障与数据库断言 |
| 越权与终态 | 拒绝且不泄露内容、不改变状态 | 绕过界面直接请求 |
| 响应和容量 | 在明确条件下记录分布与错误率 | 独立测量后确定目标 |

## 7.1 验收场景与通过标准

验收标准定义系统应满足的行为，原型检查记录证明实际观察的范围，两者分别维护。以下场景不能因为写入用例或测试脚本就直接标为通过。

## 7.2 依据核对与确认责任

核对需保留来源编号、原文位置、取得日期和适用条件，分别判断原文是否支持、产品规则是否合理、政策现行性是否取得业务确认。公开资料、产品范围决定和合成演示分开登记。业务部门意见、使用频率及服务承诺不能由AI角色讨论代为确认。

资料出现不同地点时先核事项与办理方式，不能直接判冲突；原文未给金额时不得从常识补齐。第1.5节来源登记作为本轮依据入口。

## 7.3 原型与实际检查范围

已有核心原型包括依据问答、来源展示、知识维护、工单和反馈。原型检查以功能、接口、数据库约束及受控竞争场景为对象。正常问答与快照关键接口已得到实际检查；完整回归仍发现工单事务、重复处理和部分澄清等问题，不能据此宣称原型已通过完整验收。

这份报告将原型用于发现需求歧义和实现偏差，不用代码现状反向降低需求标准。本轮依据用户要求停止继续返修，保留现有源码、测试日志与问题记录；实际结果沿用原记录，不补写通过率。

## 7.4 追踪与一致性检查

采用“来源或范围决定→用户故事/FR→用例→规则/状态→验收场景”的链条。第2.1节保留全部功能号，第4章集中规则，第5章定义状态，第7.1节列核心验收入口。新增或修改需求时同步检查关联对象、权限、时间与异常处理。

优先检查五类不一致：无来源却被当作事实、同名对象含义不同、规则与状态路径冲突、用例缺失败结果、验收只覆盖正常流程。缺乏真实确认的数据保留待确认状态，不因模型或测试采用了它就升级为已确认。
